Case Study 01 · Overview

UE5 PBR × NPR 角色渲染系统

独立完成 Technical Artist 全流程：材质层自建 NPR ＋ C++ 数据驱动运行时控制层 ＋ 渲染管线扩展插件 ＋ 编辑器工具。引擎 UE 5.7 → 5.8 启动器版，无引擎源码改动，未新增 Shading Model。脸部走真 Unlit；身体为 Lit，BaseColor 压到一成而非归零，NPR 光照在 Emissive 自算——留这一成是为了让身体仍吃到场景 VSM，同时保有 SSR / Lumen 与依赖 GBuffer 的后处理。

只描述"是什么"：StatePayload · Duration · WeightCurve

调用入口ARenderDemoController

镜头段落与状态触发时机；URenderFunctionLibrary 提供无状态工具函数

执行组件UCharacterRenderComponent

双形态：一次针对材质库的复用验证 两套形态外观差别很大，底下是同一批 master 材质，区别只在材质实例的参数与 Static Switch——master 一开始就按功能切模块（SDF 阴影、各向异性高光、POM 视差、Matcap、描边），而不是塞进一张巨图。新增形态只需建实例、调参数；改 master 的某个模块，所有形态、所有分档同步生效。

03 / 14Case 01 · 材质层
Data-Driven Runtime

状态由数据描述，由组件执行

状态数据资产携带 StatePayload、Duration 与 WeightCurve；组件逐帧计算权重写入材质实例，状态结束后按快照恢复材质基线——本质是为运行时的不确定性预设兜底路径。

类职责
ARenderDemoController演示场景总调度：镜头段落、状态触发时机
UCharacterRenderComponent按状态向各材质槽实例下发参数并回滚
URenderFunctionLibrary无状态工具：参数换算、曲线求值、安全取值
URenderQualityDataAsset三档分级开关与数值表，内置兜底默认值
灯光仲裁 · 脸部 SDF 与高光只认一个最终光 NPR 的面部 SDF、发丝高光、边缘光都需要明确的光方向，但场景里同时有主光和若干局部光。控制层每帧从 MainLight 与 LocalLight 中仲裁出唯一的 FinalLightDir / FinalLightColor / FinalLightIntensity，通过 MPC_CharacterLighting 下发给所有角色材质。

为什么必须这么做：卡通渲染依赖 ramp 查表还原立绘意图，不具备物理叠加性，多光源同时作用会污染面部色阶。代价是放弃多光源真实感，换取角色换场景、进出局部光时表现稳定可读。

04 / 14Case 01 · 运行时层
Self Shadow · PerObjectShadow 插件

头发对 Unlit 脸部投影：正交深度采集 ＋ .ush 收敛

VSM 能解决角色与场景之间的大范围投影，但头发投脸、饰品投身体这类角色内部遮挡，在二次元需求下既不够稳也不够可控。本方案从主光方向对单个角色做一次正交深度采集，在材质里比较遮挡体与接收点深度，返回 0..1 的 ShadowTerm，与已有阴影取 min() 而不是相乘，避免双重变暗。

问题处理
深度口径正交投影 ＋ R32f，全程线性世界空间 cm
精度分配ShowOnlyActors 只画目标角色；采集框缩到头骨
防闪烁bSnapToTexel ＋ Poisson 逐像素旋转 ＋ 三类 Bias
档位手段降采集频率（每 1 / 2 / 4 帧）与 RT 尺寸（0.5× 起测）；预算仍超则整块关闭
状态规划矩阵，真机 A/B 未完成；工程无独立 PCF／PCSS 过滤分档

两套自阴影，按部位分工：脸走上述自建 PerObjectShadow（纯 Unlit，转头时 SDF 阴影不能破碎，引擎阴影一点不让进）；身体挂 Lit、BaseColor 压到 SkinColor × 0.1 而不归零，留一成通路吃引擎 VSM 的角色自投影，和场景有真实阴影交互。代价已知：脸 0%、身体 10%，那一成随环境光变化，换预设时两边亮度会漂。验证：r.Shadow.Virtual.Enable 0 后身体上的角色自阴影消失，原值 0.1 下肉眼可辨。

05 / 14Case 01 · 自阴影
Render Pipeline Extension · SceneViewExtension + RDG

把内描边从后处理材质迁到引擎层自定义 Pass

新插件 NPRRenderPipeline：用 FSceneViewExtension 订阅 EPostProcessingPass::BeforeDOF，在 RDG 里插一个全局 shader Pass FNPRInnerLinePS，12 个 r.NPR.InnerLine.* CVar 驱动。两套实现长期并存，由控制器上一个布尔互斥切换，保留后处理材质版作为同机位对照入口。

问题修改
掠射角补偿算错了原用 abs(WorldNormal.z)——只看朝不朝天，与视角无关，水平面误入超敏感档。改用视空间 Nv.z。
线宽与灵敏度耦合原 smoothstep 两端都绑阈值，调线宽必改灵敏度。改为对称羽化 smoothstep(T−S,T+S,grad)。
GBuffer 解码次数材质域每 tap 解码两次；插件用 GetGBufferData(UV) 一次拿全，解码次数减半。

迁移价值的最终收敛：性能持平（两趟 0.11ms → 融合单趟 0.08ms，与原实现持平），能力无增益。主要为了"引擎层 RDG 自定义 Pass 相对后处理材质的能力展示价值"

06 / 14Case 01 · 渲染管线扩展层
Performance · 瓶颈定位

一行 cvar，52 → 60 FPS：重点是怎么找到该优化的地方

测量环境：独立进程游戏（非 PIE）· 原生 1920×1080 · CaptureEveryNFrames=4 · PerObjectShadow 开 · 固定机位 · UE 5.8 / DX12 SM6。

FRAME TIME19.12 → 16.60−2.52 ms ／ −13.2%
FPS · 原生 1080P52.3 → 60.2跨过 60 FPS 线，GI 完整保留
视觉代价0仅反射精度下降；金属走 matcap 不吃反射
真凶：Lumen 硬件光追每帧重建 BVH

角色是骨骼网格且每帧有动画，硬件光追必须每帧重建加速结构（BVH）——开销压在渲染线程，不在 GPU。换成软件追踪（SDF）把成本转到 GPU；本项目渲染线程 bound、GPU 有余量，纯赚。

档FRAMEDRAWRHITGPU

B 软件追踪 ★16.6016.6611.5612.22
C 关 Lumen13.8813.7310.208.70

A→B 的 Draw 降 4.20 ms 而 GPU 升 0.89 ms——成本转移方向一眼可见。C 档为理论下限，为保住 GI 没有采纳。同一改动在 720p 只值 2.42 ms，1080p 每帧采集下值 8.44 ms。

07 / 14Case 01 · 性能 ①
RenderDoc · Falsified Paths

用截帧把推论变成事实，并保留被数据否掉的五条路

"每个视图各重建一次 BVH"最初是数据相减推出来的；RenderDoc 截帧证实了它——过滤 RayTracingGeometry，同一帧出现两次：自阴影 SceneCapture 视图一次，主视图一次。

边界：RenderDoc 量的是 GPU 侧，能证明"结构上跑了两遍"，证明不了"CPU 成本也翻倍"——后者仍以 stat unit 为准。

路径实测判定
自阴影 RT 2048→1024省 GPU 3.03 ms，FrameTime 只降 0.21 ms证伪
分辨率 1080p→720p省 5~6 ms GPU，帧时间零变化无效
r.RHIThread.Enable 0Frame 18.75→28.74，反而恶化 10 ms证伪
r.RDG.AsyncCompute 018.29→18.05，落在噪声内证伪
r.AllowOcclusionQueries 0单次显示有效，反复切换不可复现证伪

渲染线程 bound 的项目里，只动 GPU 的优化换不回帧率。读数可信度判据：Draw≈Frame 且 RHIT 行存在→环境正确；同配置运行间波动约 ±1.4 ms，跨运行差值 <1.5 ms 不算收益。

一次真实的纠错：先证据，后动手

我一开始以为毛领要运行时实例化 32 层几何壳，写了 32 个 SkeletalMeshComponent，帧数暴跌。逐槽隔离定位后，改为像素着色器视差展开壳层，删掉几何壳后帧数恢复，画面效果也很好。结论：游戏内无法大量实例化，制作材质效果时必须先考虑运行时帧数。

Case Study 03 · Art Pipeline

AI-DCC → UE5 美术资产流水线

痛点：DCC 到 UE5 的资产交接依赖人工目检，命名、Transform、UV、材质槽等问题在我与他人的流程里反复出现——说明是流程缺陷而非个人疏忽。源码：github.com/hunshuiDD/ai-dcc-ue5-pipeline

维度做法
导出前Blender 插件预检命名、缩放、材质槽、UV 与法线，定位到具体对象；模型与 metadata、JSON / CSV 报告同名落盘
UE 规则库自研 UE 5.8 C++ 编辑器插件：规则 / 规则组 / 规则集，12 种比较算子，组合规则沿“模型 → 材质 → 贴图”展开
资源审查贴图、静态网格、骨骼网格属性审查；按资产注册表匹配、按需加载；结果可筛选、定位，豁免必须写原因
可验证640 项离线测试（628 通过、12 跳过、0 失败）；C++ 与 Python 共用契约，写出的规则逐字节一致
边界读不到就报错，不默认放行；工具只报告不改资产；MCP 封装管线阶段，写入需授权、关卡需人工签字
AI 解释分析只把 JSON 报告翻译成人读的修复计划，经人工确认后才落到资产上；判定全部来自确定性规则
工具优点

这套工具解决的正是"美术资产的制作规格与标准规范如何落地"——规范写在文档里靠自觉，写成规则才能在每次导出时被执行，并在不合规时直接阻断导入。

局限

导入检查与管线 Tab 已通过自动化测试，尚未人工验收；受控导入目前只覆盖静态网格；人工流程基线未测，暂不写提效数字。

技术栈与工作方式

引擎与渲染

UE 5.7 → 5.8；材质编辑器与 Custom HLSL；NPR 卡通渲染（SDF 面部阴影、各向异性高光、POM 视差、Matcap、内外描边）；Substrate 下的 PBR 材质；一阶 SH 间接光；Lumen / SSR / GTAO 的开销与取舍。

引擎层扩展

FSceneViewExtension ＋ RDG 自定义 Pass；IMPLEMENT_GLOBAL_SHADER 与 .usf 虚拟路径映射；CVar 参数通道；D3D12 验证层读 PSO 创建失败原因。角色渲染项目均在插件内完成；个人面部 SDF 在 UE 5.8.3 完成光向和像素复验。

性能与调试

stat unit · ProfileGPU · csvprofile · Unreal Insights · RenderDoc 截帧 · Shader Complexity / Quad Overdraw。习惯做单变量 A/B 对照并给出噪声阈值，不采信跨运行的小差值。

工具与管线

C++ 运行时控制层（Data Asset / Component / Project Settings）与编辑器插件；UE Python 与 Editor Utility Widget；Blender Python；资产审计、命名规范检查与导入后复检。

工作方式
  • 先证据，后动手。五条看似必然有效的优化路径被自己的实测否掉并保留在案；毛领 32 层几何壳的方案在帧数暴跌后被推翻重做。
  • 分层归因。七个调试视图与四层架构的目的一致——让任何一个异常都能定位到具体一层，而不是靠试参数。
  • 诚实标注边界。未验证的数字宁可空着；迁移的收益被实测推翻就照原样写出来，不改口径包装成收益。
